# 个人 App 提炼到入库的完整闭环

状态：用户于 2026-09-07 确认方案，现已实现并完成隔离开发 / 打包 App 验收。真实模型调用仍由用户在 App 内确认；证据与边界见实施计划的验证记录。

## 目标与范围

用户已明确要求补齐全链路：插件保存 Markdown → App 识别并归档 → 提炼 → 审阅和编辑候选 → 确认入库 → 知识库中找回并追溯原资料。操作均在个人 App 内完成，保持当前暗色、绿色重点色、左侧导航与双栏工作台。

本次不是 SaaS、批量自动提炼、无人确认自动入库，也不是重做图书馆归档。沿用已经工作的识别与归档能力，补齐提炼可靠性、候选审阅、正式写入、状态联动、检索与恢复。

## 实施前代码事实

- `ExtractionPage.tsx` 的成功页只展示 briefing 与候选，明确写着入库尚未接通。
- `personal_extraction_runs` 保存整次结果，没有可编辑候选、逐条取舍、入库批次和回执。
- 当前候选字段只有标题、类型、目录、主题、核心内容、价值；不能直接当成符合仓库规则的完整知识笔记。
- `extraction-service.ts` 把结构校验、目录、主题、超限等多种失败合成一句错误。当前真实失败 run `6ea1a9e5-f880-4fb3-bc20-ddd612fe08b7` 无结果；不能从这句话还原某个具体失败字段，也不能声称已找回模型回答。
- 已离线复现契约缺口：省略 `briefing.caution` 可通过，空串或 `null` 失败；提示词未明确这个区别，也未完整说明文字长度和额外字段限制。这是确定的缺陷，不等于已确定真实失败 run 的具体原因。
- `atomic-file-helper.c` 当前接入的是只读协议；已有 personal archive 写能力限于 clipper 入馆，不能直接当成正式知识入库器。
- 旧 Phase 4 文档描述了规划中的多文件写入能力；不能把计划中的类当作已经实现的基础设施。

## 方案选择

1. **推荐：一次提炼生成完整草稿，在 App 审阅后确认一批入库。** 保留人工取舍，正常流程不需要再次找 Agent 或补写 YAML。
2. 先展示短候选，选中后再调用模型生成笔记：初次等待较短，但多一次模型请求与等待；不作为默认流程。
3. 模型生成后直接全部入库：操作更少，但取消了用户明确取舍，与现行入库规则不符，不采用。

## 用户操作与可见结果

1. **发送提炼。** 显示真实运行状态；可以离开后回来，不显示虚构进度。结果保存在本机，失败保留具体原因和手动重试入口。
2. **审阅候选。** 在原工作台中显示“待处理 / 已入库 / 已放弃”以及数量。每条可编辑、选入本批、稍后处理或明确放弃。未勾选不等于放弃。编辑草稿自动保存到本机，显示保存状态；保存失败时保留当前编辑并阻止错误的成功提示。
3. **核对知识。** 常用编辑区放标题、正文、分类；召回字段按需展开。完整内容、知识类型、关键词、结论、场景、要点、边界、可复用表达都可查看修改；来源与已有状态不能被普通表单随意改掉。候选不可假装是已认可知识。
4. **判断新增或合并。** 自动检索目标及相邻目录的标题与 YAML 召回字段，显示相关旧笔记、匹配依据和使用状态。用户可查看旧文、选择新建或选择合并目标。检索失败不得当作“没有重复”；不把关键词相似当作确定相同。
5. **预览本批变化。** 明确显示新建与更新的笔记、实际目录、全文或差异、原资料将更新的回链与入库状态。一次“确认入库”只授权当前可见批次；无需逐条再弹确认。返回修改会使旧预览失效。
6. **完成并找回。** 展示实际生成或更新的笔记链接、还有多少候选未处理。可在 App 内打开笔记、跳回原资料、继续剩余候选或下一份资料。已写入但索引未就绪时显示“已写入，正在更新检索”，不能报成需要重复入库。

窄窗口沿用列表/详情切换，底部批次操作保持可见；不再堆叠多个独立卡片页面。明确离开、保存中、冲突、恢复和零候选的状态。

## 候选与笔记契约

- 新结果使用版本化契约：一次模型请求生成可审阅的完整知识草稿。知识笔记 YAML、固定正文结构、状态和引用约束以当前 `00`、`03`、`05` 为准，不另创规则。
- 从同一个契约生成提示中的字段、枚举、长度和目录约束；保留零候选合法。只允许不改变内容含义的明确格式归一化，不填造结论、不静默截断正文、不把不合格结果降格当作合格。
- 保存可公开显示的错误类别与字段位置，区分输出截断、JSON 结构、字段、目录及超限；不记录密钥或把模型返回值原样拼进错误。重试仍由用户点击，不新增后台自动模型调用。
- 已有 v1 成功结果保留不动。打开时转换为可编辑草稿，缺少的正式笔记字段明确标为待补齐；允许在 App 内补齐，或明确预览并重新提炼，不能自动重发。
- 新建知识默认 `来源类型: AI提炼`、`使用状态: AI总结`。来源资料、日期和回链由服务端按已核对信息生成。没有真实原文引用时写规则规定的空引用说明。
- 目标目录必须真实存在；主题只能选择真实或已有明确批准计划的主题，不自动建目录或主题。

## 新增、合并与旧笔记保护

- 新建时不得覆盖同名文件，不通过自动加编号绕开冲突。界面让用户修改标题或选择已有笔记。
- 合并 `AI总结`：展示完整更新结果及差异，保留已有来源，确认后状态不变。
- 合并 `已优化`：保留已认可内容；新判断/步骤/边界等按规则标 `==AI待认==`，包括引用这些新判断的 YAML 召回项和备注日期。不能借本批入库自动认可。
- `定论` 只接受不改含义的来源补充；有新判断则保留为独立候选，不在本批暗中解锁。`过时` 不作为继续累积活跃知识的目标。
- 多来源合并必须保留已有出处并生成规则要求的小节来源映射。无法判断来源归属时要求在编辑区明确，不能覆盖原有归属。
- 一个批次里多个候选指向同一目标时，应合并成一个可预览的目标版本；不能顺序覆盖彼此内容。

## 持久状态与写入边界

拆成可独立验证的模块：

- **CandidateReviewService**：稳定候选 ID、可编辑版本、保存与取舍状态。原始模型结果不可变，编辑草稿与其分离。多窗口修改使用版本检查。
- **KnowledgeMatchService**：本地目标/相邻目录召回、匹配依据与精确目标读取；不为查重自动发送其他知识正文给模型。
- **IngestionPlanner**：读取当前规则、原资料、所选草稿和目标文件；输出确定的笔记字节、来源 YAML 变化、哈希与差异。预览本身不写仓库。
- **PersonalIngestionCoordinator + scoped native writer**：在实际 personal vault 上补齐正式入库能力；不放开通用任意路径写入，也不复用入馆路径规则冒充入库。保存持久批次、原始版本、预期版本和写入回执，处理幂等提交、复读和中断恢复。
- **IngestionFinalizer**：验证文件、YAML、来源双链与原文正文保真后，落候选提交状态，触发索引并提供最终查找入口。

正式批次绑定候选版本、规则指纹、来源及目标版本。首次确认前重新核对；有外部变化则保留草稿、要求更新预览。批次按“知识文件先、原资料最后”执行；原资料只更新必要 YAML 字段，原正文和附件字节不变。保留原有 `生成知识` 链接并去重，不替换整份来源记录。

多文件不能被描述为一次文件系统原子事务：每一步有可核验回执与恢复记录。失败不得伪报全部成功。重启后根据磁盘状态恢复同一批次；未确认的预览不执行。出现外部改动时保留各版本，在 App 展示受影响文件与可确认的解决方式，不要求用户去终端处理，不自动覆盖外部编辑。

现有 macOS 交换操作并不提供来源内容的原子 hash CAS。新实现必须测试“核对后、交换前发生外部原地修改”的竞争窗口；保留交换前后的版本并进入待解决状态，不能以一次预检查宣称外部改动绝不会与写入交错。恢复记录与 before/after 内容须在第一次仓库改动前完整持久化。

重复点击、请求响应丢失、刷新或重启以同一批次 ID 找回结果，不再次生成文件。同一路径在未完成批次中不能再被另一批次写入。索引失败只重试索引，不重放已完成的文件写入。

## 来源与队列的状态联动

- 尚无正式入库：保持 `未提炼`；仅编辑、保存、发送或取得候选不改 YAML。
- 已有入库且有候选待取舍：`部分入库`。剩余候选在工作台可继续，不要求重新发模型请求；原资料因本 App 回写 YAML 而产生的新 hash 不得误报旧候选失效。
- 需保留的均已写入，其余均明确放弃：`已入库`。
- 零候选或全部明确放弃且零入库：工作台显示“本轮已处理，无需入库”，不伪造知识文件或入库数量；原 YAML 保持 `未提炼`。作为 App 内已处理记录保留，可手动重新提炼。
- 首页牌堆不出现 `部分入库` 或 `已入库`；本轮已明确结束、无需入库的资料也不反复占用待处理位置，数量文案区分“待处理”与 YAML 入库状态。
- 当前列表保留待提炼、提炼中、已有结果、未完成，在已有结果中增加待处理/已处理分组；已有历史入口不丢失。
- 一个来源有多次结果时，不能仅按最新一次推算完成：旧版已入库链接保留，未决候选不能被新结果悄悄放弃。更换审阅轮次需明确显示旧轮次未决项，并由用户选择继续或放弃；重复知识仍走查重。
- 原资料正文或非 App 管理字段被外部改动，必须更新预览或重新提炼；不能只凭路径相同就沿用旧证据。由本批回写导致的版本变化在批次链上明确记录。

## 完成标准

交付必须是实际打包 App，以下流程在隔离资料库中从界面跑通，再由用户用真实资料确认：

1. 插件式新增 Markdown 能进入收件箱，归档后在工作台开始提炼。
2. 生成至少两个完整候选；编辑其中一条并重启，草稿仍在。
3. 确认一条新建或合并：真实 Markdown 可读、来源双链正确、原正文及附件不变；剩余待处理使来源为部分入库，首页牌堆移出该资料。
4. 处理剩余候选后，状态正确收口；在知识库通过标题/关键词找回，并在 App 内追溯原资料。
5. 格式错误、超时、零候选、全部放弃、同名目标、保护状态、外部修改、重复提交和写入中断都有正确可操作的结果。
6. 请求已完成但响应丢失、文件写完但索引失败等情况不重复入库、不丢取舍状态。开发版与打包版都验证，不能只靠模拟组件宣称真实链路完成。

自动测试使用隔离 vault 和受控模型响应，不重归档真实资料、不触发真实模型收费、不代用户确认真实候选入库。真实 DeepSeek 效果需要用户在 App 明确确认发送后验证；当前失败记录保持可查。

## 实施顺序

1. 对齐提炼契约并补具体失败诊断，验证已有结果兼容。
2. 落地候选草稿、取舍和新增/合并预览。
3. 实现并验证受限原生写入、批次恢复与来源回链。
4. 接通确认入库、知识详情入口、队列与首页状态。
5. 完成隔离全链路、故障恢复、宽窄屏及打包验证，更新 README 中真实可用范围。

这些是同一交付的依赖顺序，不把“只显示候选”或“只加一个入库按钮”算作最终完成。
