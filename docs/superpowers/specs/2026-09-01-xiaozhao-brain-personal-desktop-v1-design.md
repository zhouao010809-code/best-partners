# 小兆大脑个人桌面版 V1 设计规格

- 日期：2026-09-01
- 状态：对话设计已确认，待书面复核
- 产品形态：仅供本人使用的 macOS 本地桌面 App
- 正式数据真源：`/Users/ao/我的大脑` 中的 Markdown、YAML、附件与双链
- 首版核心闭环：插件采集 → 自动入馆 → AI 提炼 → 人工审阅 → 安全入库 → 知识编辑 → 恢复与追溯

## 1. 决策背景与规格优先级

现有工程已经完成一套黑色玻璃风格的 Phase 1 只读 Web 控制台，但它仍依赖命令行启动、环境变量和 Obsidian Local REST。提炼工作台与写入确认仍是占位页面，不能完成正式入库，也没有桌面安装包。

本轮确认把产品目标从“以后可能成为 SaaS 的本地 Web MVP”收紧并扩展为“用户本人现在可以每天使用的个人桌面 App”：

- 先不做 SaaS、账号、团队、多租户、订阅或云端服务。
- 双击 macOS App 即可使用，不需要终端。
- Obsidian 没有打开时，浏览、编辑、提炼和入库仍然可用。
- 所有日常知识操作在 App 内闭环，不把正式确认退回 Obsidian 手工完成。
- App 直接读取和受控写入正式 vault；Obsidian 只保留为可选查看与编辑工具。
- 现有插件继续负责采集，并把 Markdown 与附件投递到 `01图书馆/小兆clipper`；App 自动识别和入馆。
- V1 暂定使用 DeepSeek，接口层保持 OpenAI 兼容。

本规格在发生冲突时，取代旧的“本地 Web 管理台”产品形态、Local REST 运行依赖、只读知识详情和“不做采集/完整编辑器”等决策。旧的 Phase 2、Phase 3 实施计划仍可复用领域模型与安全思想，但不得不经重写直接执行。

## 2. 产品定义

小兆大脑个人桌面版是现有 Obsidian 大脑之上的本地工作系统，而不是另一份数据库副本：

- Markdown、YAML、附件和双链继续是唯一正式数据。
- SQLite 只保存可重建索引、未完成草稿、任务状态和操作记录。
- AI 只能生成结构化提炼候选和修改建议，不能绕过用户确认直接写入。
- 用户在 App 内完成最终审阅、差异确认、写入、编辑和恢复。
- App 不改变 `00大脑规则` 的权限、目录、YAML 和状态语义。

### 2.1 V1 成功定义

V1 只有同时满足以下条件才称为“最终可用版”：

1. 用户从 `.dmg` 安装或直接双击 `.app`，无需终端即可进入主界面。
2. Obsidian 关闭时，App 可以扫描、搜索、查看、编辑和安全写入大脑。
3. 插件放入 `小兆clipper` 的完整资料包会被自动发现、稳定性检查并入馆。
4. 用户可以在 App 内完成一条真实资料从未提炼到已入库的完整流程。
5. 用户可以直接编辑已有知识的 YAML 与 Markdown，并在保存前查看差异。
6. 在通过 macOS 原子交换契约测试后，外部文件变化、写入冲突和进程崩溃不会造成静默覆盖；提交瞬间观察到的文件版本和事务 before/after 字节均可追溯。
7. 侧边栏在桌面窗口中始终位于左侧；窄窗口只收缩为图标栏，不变成底部导航。
8. 总览牌堆只展示 `知识入库状态: 未提炼` 的资料。

## 3. 明确不做

- 不做 SaaS、登录、组织、团队、权限、租户、订阅或远程访问。
- 不做手机端、Windows 或 Intel Mac 通用发行；V1 先服务当前 Mac。
- 不做面向外部下载的公开发行；Developer ID 签名、公证与跨机器 Gatekeeper 免提示不属于个人 V1。
- 不重做浏览器采集插件；App 接收插件已经落盘的资料。
- 不实现批量改写、批量入库或无人审阅的自动写回。
- 不提供永久删除知识的产品操作；停用知识走 `使用状态: 过时`。
- 原始资料始终禁止删除和正文改写。
- 不在 V1 中新增或治理一级/二级核心目录、YAML 字段、枚举、路由、权限边界或主题节点。
- 不实现 `03大讲堂` 内容生产、发布和飞书同步。
- 不把整个 vault、API Key、完整模型请求或原文副本同步到云端。
- V1 搜索范围为标题、路径和 YAML 召回字段；不承诺正文全文检索、OCR、音视频转写或通用文件解析。

## 4. 信息架构

### 4.1 固定左侧导航

主导航固定为五项：

1. **大脑总览**：状态、统计、未提炼牌堆、最近知识和下一动作。
2. **提炼队列**：未提炼、部分入库、待确认入馆和未完成任务。
3. **知识库**：搜索、筛选、查看和编辑正式知识。
4. **操作与恢复**：入馆、提炼、编辑、写入、冲突、失败和恢复记录。
5. **设置**：vault、DeepSeek、安全存储、监听与应用状态。

以下流程页面不占用侧边栏，只从当前任务进入：

- **提炼工作台**
- **入库确认**
- **知识编辑器**
- **冲突处理与恢复详情**

侧边栏在正常桌面宽度显示图标和文字；窗口变窄时收成左侧图标栏。V1 不采用底部移动导航。

### 4.2 全局入口与状态

- 顶部显示本地索引、文件监听、DeepSeek 和恢复锁状态。
- 全局通知以需要用户处理的事件为主，例如入馆无法判断、模型失败、文件冲突或待恢复写入；自动入馆成功使用非打扰式提示和未读角标，不弹阻断对话框。
- 现有“系统连接”页面并入“设置”；连接诊断仍保留，但不再把 Obsidian Local REST 作为必需连接。

## 5. 核心用户流程

### 5.1 首次启动

1. Electron 主进程启动内嵌本地服务和 SQLite。
2. 默认探测 `/Users/ao/我的大脑`；若路径不存在或不符合规则，显示系统文件夹选择器。
3. 校验 `00大脑规则`、四区目录和 App 数据目录互不包含。
4. 要求用户在设置中填写 DeepSeek API Key，并使用 macOS 安全存储加密保存。
5. 完成第一次只读扫描后进入总览；未配置模型不影响浏览、搜索和编辑。

### 5.2 插件采集与自动入馆

主入口仍是：

```text
01图书馆/小兆clipper
```

流程如下：

1. 浏览器插件把 Markdown、图片和其他附件写入 `小兆clipper`。
2. App 运行时监听文件事件；App 关闭期间产生的资料在下次启动时由全量对账补扫。
3. 资料包的路径、大小和修改时间连续稳定后才进入解析，避免读取半写入文件。
4. App 按现行规则确定主 Markdown、来源平台、采集日期、月份目录和规范名称。
5. 高置信度资料自动补齐允许的 YAML 字段，并把整个资料包移动到 `来自某平台/YYYY-MM`。
6. 来源、主 Markdown 或目标冲突无法判断时，保持原文件不动并进入“待确认入馆”。
7. 入馆只调整允许的 YAML 字节片段和路径，原始正文与附件保持不变。
8. 成功后固定为 `处理状态: 已归档`、`知识入库状态: 未提炼`，重新索引并进入未提炼牌堆。

V1 不要求额外的手工粘贴入口；现有采集插件是主要采集端，App 是识别、入馆和后续处理端。

### 5.3 未提炼牌堆与队列

- 总览牌堆只接收 `未提炼`，不显示 `部分入库` 或 `已入库`。
- 牌堆详情只有一个主动作：`开始提炼`。
- 队列可查看 `未提炼`、`部分入库`、待确认入馆和未完成工作流。
- `部分入库` 只在队列中显示 `继续处理`，不回到牌堆。
- `已入库` 不进入默认待办，但仍可从知识和操作记录追溯。

### 5.4 AI 提炼工作台

提炼工作台采用三栏结构：

| 区域 | 内容 | 权限 |
|---|---|---|
| 左栏 | 原始资料、来源元数据、搜索和证据定位 | 原文只读 |
| 中栏 | 候选列表、状态与批次进度 | 选择和取舍 |
| 右栏 | 标题、类型、路径、召回字段、正文、价值、来源证据和重复知识 | 编辑草稿 |

工作流遵循现有阅读状态规则：

- 无明确证据时默认 `未看`。
- `未看` 先展示资料概述、主要知识点、用途和必要提醒，再进入候选。
- `已看` 可直接进入候选。
- 阅读状态只保存在本地工作流，不写回来源 YAML。

DeepSeek 请求遵循以下边界：

- 只发送当前资料的必要原文、允许的来源元数据和少量去重上下文。
- 发送前在 App 内提供可查看的内容预览、字节数、脱敏项和模型目标。
- 模型没有文件工具、路径写入权限或正式状态决定权。
- 返回结果必须经过结构校验；失败不会产生正式文件变化。

每条候选可反复编辑，并在写入批次准备前切换：

```text
待确认 <-> 已接受
待确认 <-> 已放弃
已接受 <-> 已放弃
```

完成整轮入库前，所有候选必须完成取舍。用户也可以显式选择“先入库已确认项”，只提交已经接受且已选定新建/合并目标的候选；其余候选保留在当前批次中继续处理。候选修改会让涉及它的旧写入计划失效并重新生成差异。

### 5.5 入库确认

每条接受的候选必须明确选择：

```text
新建知识
合并已有知识
返回继续编辑或放弃
```

App 必须显示：

- 目标路径和知识类型。
- 完整 YAML 与 Markdown 预览。
- 新建或合并的逐行差异。
- 来源资料将更新的 `生成知识` 和 `知识入库状态`。
- 本批次涉及的全部文件与执行顺序。
- 当前文件版本检查与可恢复状态。

写入成功后的状态严格采用现行定义：

- 尚未正式写入任何候选，且本轮仍未结案：保持 `未提炼`。
- 至少一条候选已经正式写入，但仍有候选等待决定或等待写入：`部分入库`。
- 本轮候选已全部成功写入或明确放弃：`已入库`；全部候选都被放弃时也通过一次来源状态确认完成结案。

知识文件始终先写，来源 YAML 最后写。只有全部写入、复读、schema、双向链接和 hash 校验通过后，操作才显示成功。

### 5.6 直接编辑已有知识

知识详情提供显式“编辑”动作：

- YAML 使用受控表单，不允许任意新增字段或枚举。
- 正文使用 Markdown 编辑器和同步预览。
- 编辑过程自动保存到 vault 外的本地草稿，不自动改正式文件。
- 保存前生成完整差异；用户确认后才进入正式写入事务。
- 打开编辑器时记录原始 hash；外部变化会使草稿进入冲突态。

状态保护直接编码现行规则：

- `AI总结` 可在确认后更新，状态默认不升级。
- `已优化` 的新观点、步骤、边界、反例或修正使用 `AI待认` 标记；仅补充来源、例子或证据时保持原状态。
- `定论` 默认禁止 AI 改写；只有用户在 App 内显式解除并确认后才能修改受保护内容。
- `过时` 不继续累积活跃知识；新内容优先进入替代笔记。
- 改为 `过时` 必须显示原因、替代关系和影响并再次确认。

V1 没有永久删除按钮。已提交操作需要撤销时，使用“恢复为写入前版本”，并把恢复本身记录成新的受控事务。

### 5.7 操作与恢复

每个操作记录：

- 操作类型、目标路径、开始和结束时间。
- 模型与校验状态，但不记录 API Key 或完整敏感请求。
- 每一步的 before/after hash、结果和错误代码。
- 用户确认、写入计划、恢复快照和最终状态。

发现未完成写入时，App 启动后先进入恢复模式：

- 锁定相关路径，暂停新的正式写入。
- 显示已完成和未完成步骤。
- 允许根据当前 hash 明确选择“继续”或“回滚”。
- 无法安全自动处理时保留所有版本并要求人工选择，不猜测覆盖。

## 6. 正式数据与本地状态

### 6.1 数据真源

正式投影继续使用 vault 相对路径与原始字节 hash：

```ts
type FileVersion = {
  path: string;
  exists: boolean;
  rawSha256?: string;
  byteLength?: number;
  modifiedAt?: string;
};
```

不向现有 YAML 添加未确认的稳定 ID。重命名会使旧路径身份失效，并由索引对账和工作流冲突处理接管。

### 6.2 SQLite 边界

SQLite 只保存：

```text
SearchIndex
SchemaIssue
IntakeJob
ExtractionRun
CandidateDraft
CandidateDecision
WritePlan
WriteBatch
WriteStepResult
EditorDraft
AuditEvent
```

以下内容不得把 SQLite 当成唯一副本：

- 正式 Markdown/YAML。
- 原始资料和附件。
- 可重建的知识正文副本。
- DeepSeek API Key。
- 写入恢复所需的唯一 before/after 字节。

### 6.3 应用数据目录

App 数据使用 Electron `app.getPath('userData')` 下的专用目录，且必须位于 vault 外。目录包含：

```text
config/
state/
drafts/
recovery/
backups/
logs/
```

- 配置、数据库、草稿、恢复材料和日志不进入 Obsidian。
- DeepSeek Key 只在用户输入瞬间由隔离渲染页通过单用途 IPC 传给主进程；主进程使用 Electron `safeStorage` 加密后落盘。之后不向渲染进程回传明文，只返回“已配置/未配置”。
- Key 不进入剪贴板持久化、日志或崩溃报告。`safeStorage` 依赖当前 macOS 用户钥匙串，不承诺抵御已经控制该用户会话的恶意程序。
- 日志不得记录密钥、完整原文、完整模型请求或恢复字节。
- `userData`、`recovery` 和 `backups` 使用当前用户私有权限：目录 `0700`、文件 `0600` 或 macOS 等价权限；敏感恢复材料不写入系统临时目录。

## 7. 技术架构

### 7.1 Electron 桌面壳

保留现有 React、Fastify、SQLite 和共享 Zod 契约，新增 Electron 主进程：

1. 取得单实例锁。
2. 解析 vault、用户数据和安全配置。
3. 启动内嵌 Fastify 服务。
4. 让系统分配空闲 loopback 端口。
5. 从同源 `http://127.0.0.1:<port>` 加载构建后的 React 页面。
6. App 退出时依次停止监听器、索引器、Fastify 和 SQLite。

渲染进程保持 `contextIsolation: true`、`nodeIntegration: false` 和 sandbox。只通过最小 preload 能力调用系统文件夹选择、应用版本、外部打开和安全配置动作；业务数据继续走同源 HTTP API。主窗口拒绝非主 origin 导航、任意新窗口和未列入白名单的外部协议。

不使用 `file://` 加载主应用，以保留现有 Cookie、CSRF、CSP、Host 和 Origin 安全边界。

### 7.2 内嵌本地服务

现有有副作用的服务启动代码拆成可调用的 `startServer(config)`，生产版同时提供：

- `dist/client` 静态资源与 SPA fallback。
- 本地 API 和事件流。
- 动态端口对应的 Host/Origin 校验。
- 索引、监听、提炼、写入和恢复服务。

服务只监听 `127.0.0.1`，不开放局域网地址。每次启动生成不可预测的会话凭证，由主进程通过 `HttpOnly`、`SameSite=Strict` Cookie 或等价启动握手建立专用 session；所有变更 API 同时校验 session 与 CSRF。Host、Origin、CSP、请求大小和路径校验继续保留。

该威胁模型用于阻止 drive-by 网页、跨站请求和误访问，不承诺抵御已经取得当前 macOS 用户权限的本机恶意进程。

### 7.3 文件系统 Vault Gateway

`FileSystemVaultGateway` 取代运行时必需的 `LocalRest51Gateway`，负责：

- 按允许目录遍历和读取原始字节。
- 拒绝路径逃逸、隐藏目标、符号链接越界和超限文件。
- 计算稳定 SHA-256 和文件元数据。
- 通过受测的 macOS 原子文件 helper 支持排他创建、原子交换、排他移动和条件恢复。
- 可选通过 `obsidian://` 在 Obsidian 打开文件，但不依赖 Obsidian 运行。

`LocalRest51Gateway` 可保留为测试或可选集成，不再决定 App 能否启动或写入。

直接文件写入设独立能力闸门：原生 helper 必须在当前文件系统上证明 `RENAME_EXCL`、`RENAME_SWAP` 或等价语义、目录 fsync、冲突保留和崩溃恢复。闸门未通过时，App 仍可读取、搜索、生成草稿和预览差异，但所有正式创建、替换、入馆移动和恢复操作保持关闭。

### 7.4 文件监听与对账

文件事件只用于加速，不作为正确性的唯一来源：

- 启动时全量对账允许目录。
- 窗口重新聚焦时执行轻量对账。
- 运行时监听新增、修改、移动和删除事件。
- 写入前后都直接复读目标，不相信旧索引。
- 监听丢事件或 App 长时间关闭时，下一次对账仍能恢复一致状态。
- 当前规则 bundle 的内容 hash 发生未知变化时，读取与搜索继续可用，自动入馆、候选生成和正式写入保持关闭，直到兼容性重新验证。

### 7.5 DeepSeek

V1 默认提供一个 OpenAI 兼容模型适配器，设置页显示：

- 服务地址。
- 模型名。
- API Key 配置状态。
- 连通性测试与最近一次安全错误。

默认预设 DeepSeek，但不把具体模型名硬编码为业务规则。切换其他 OpenAI 兼容模型只改设置，不改变提炼、校验和写入协议。

## 8. 写入安全协议

### 8.1 写入计划

任何正式变更都必须先生成不可变 `WritePlan`：

- 包含全部目标路径、预期 before hash、after bytes/hash、操作顺序和计划 hash。
- 知识操作在前，来源状态更新永远最后。
- 所有 after 内容先在内存中重新解析并通过当前规则校验。
- 任意候选、草稿、路径、文件版本或规则版本变化都会使计划失效。

### 8.2 恢复材料先行

第一次正式修改前，App 在 vault 外写入并 fsync 自包含 manifest：

- 完整有序计划。
- 每个目标的 before/after bytes 与 hash。
- 当前步骤、结果和校验和。
- 继续与回滚所需的全部条件。

manifest 不依赖 SQLite 才能解释。它使用追加式 journal，或使用 `temp + rename + 文件 fsync + 目录 fsync` 更新；每一步都先记录 intent 并持久化，执行后再记录 result 并持久化。SQLite 损坏时，App 仍可进入最小恢复模式。

恢复时以磁盘实际 hash 推断步骤状态。只有当前版本命中该步骤的 before/after 条件时才允许继续或回滚；否则只允许保留、导出和人工选择各版本，不自动覆盖。

### 8.3 本地文件替换

正式替换通过 macOS 原子交换 helper 完成：

1. 先把计划中的 expected before bytes 写入 vault 外恢复区并 fsync。
2. 在目标同目录排他创建临时文件，写入 after bytes 并 fsync。
3. 持久化本步骤 intent，紧邻提交前复读目标并核对 expected hash。
4. 使用 `renamex_np(..., RENAME_SWAP)`、`renameatx_np(..., RENAME_SWAP)` 或经契约验证的等价原子交换，把 target 与 temp 在一个原子操作中互换。
5. temp 此时持有提交瞬间的旧 target；核对其 hash。若不等于 expected before，则依据当前 target/temp hash 条件交换恢复并进入冲突，所有观察版本都保留。
6. 若匹配，归档 temp 中的旧版本，持久化 result，并 fsync 目标父目录。
7. 复读 after bytes、hash、YAML、正文结构和双链。

新文件和资料包移动使用 `RENAME_EXCL`、`O_EXCL` 或经契约验证的等价排他语义；目标已存在即冲突。任何阶段发现额外版本都保留全部字节并进入恢复，不静默选择一个版本。

App 内部写入使用单一协调器串行执行。它不能强迫外部编辑器参与锁，因此原子交换闸门、提交前后核对、事务 journal、版本保留和冲突 UI 缺一不可；helper 或文件系统不满足契约时不降级为普通 `rename(temp, target)`。

### 8.4 YAML 与原文保护

- 入馆和来源回写只对已批准 frontmatter key 的精确字节范围做定位式补丁；未知字段、注释、字段顺序、换行和其余字节必须保持一致。
- 无法无损定位 frontmatter 时停止并进入待确认，禁止把来源 YAML 整段 parse/stringify 后回写。
- 原始资料除被批准字段的精确字节范围外，整个文件其余 bytes 必须逐字节保持一致；附件 bytes、相对路径和包内链接也保持不变。
- 知识模板由服务端确定，不允许模型生成 frontmatter 边界或任意字段。
- 新建知识只进入现有合法目录；目录治理不作为候选写入的隐式副作用。
- 直接编辑器可以修改知识正文，但仍必须通过 schema、状态保护、差异和确认流程。

### 8.5 已提交版本与恢复保留

- 未完成或失败事务的恢复材料保留到用户明确继续或回滚完成。
- 已成功提交的 before 快照默认保留 30 天。
- “恢复为写入前版本”会重新检查当前 hash，生成新的反向 WritePlan，并作为新操作记录；不会直接覆盖后续修改。
- 成功事务超过保留期后可自动清理；未完成事务只有在恢复完成后才能由用户明确清理。

## 9. 错误处理

| 场景 | App 行为 |
|---|---|
| vault 不存在或规则缺失 | 停止索引与写入，进入设置修复 |
| DeepSeek 未配置或断网 | 浏览和编辑继续可用，提炼显示可重试状态 |
| 采集资料仍在写入 | 保持等待，不读取半成品 |
| 入馆来源或主文件不明确 | 保持原路径，进入待确认 |
| schema 不合法 | 排除正式队列，显示具体字段与路径，不猜测修复 |
| 外部文件已变化 | 使草稿或计划失效，显示新旧差异并要求重载 |
| 目标路径冲突 | 禁止写入，返回新建/合并选择 |
| 写入步骤失败 | 锁定涉及路径，进入继续或回滚流程 |
| SQLite 损坏 | 禁止普通写入，仅开放恢复与安全重建索引 |
| App 意外退出 | 下次启动先扫描 manifest，再开放普通工作区 |
| 规则 bundle 未知变化 | 保持读取可用，关闭自动入馆、候选生成和正式写入 |

所有错误必须使用用户能理解的中文说明，并保留操作 ID 供诊断；不能只显示堆栈、HTTP 状态码或“未知错误”。

## 10. 视觉与交互约束

沿用已经确认的黑色玻璃控制台方向：

- 近黑舞台、深色玻璃面板、银灰边缘与荧光绿主强调。
- 红色只表示失败或冲突，琥珀色表示待确认，蓝色表示辅助信息。
- 信息密度高但层级清楚；长文编辑区减少玻璃模糊和强光。
- 状态同时使用文字、图标和颜色，不依赖单一颜色。
- 牌堆保留纵深、展开、键盘操作和 reduced-motion。
- 关键写入必须使用显式按钮和完整差异，不能由长按、回车卡片或路由跳转触发。
- 所有桌面验收宽度中侧边栏保持左侧；窄窗口只收缩，不下沉到底部。

## 11. 测试与验收

### 11.1 自动化层级

- **单元测试**：规则解析、路径边界、原始字节保护、模板、hash、状态机和计划确定性；来源 frontmatter 使用 golden bytes 覆盖未知字段、注释、CRLF、BOM、无结尾换行和中文链接，证明非目标字节完全不变。
- **集成测试**：带测试哨兵的临时测试 vault 中验证入馆、索引、提炼持久化、知识编辑、原子交换、冲突和恢复。
- **组件测试**：所有页面的 loading、empty、error、conflict、recovery、键盘与可访问状态。
- **端到端测试**：从插件夹具落盘到自动入馆、未提炼牌堆、提炼、差异确认、写入、搜索和恢复。
- **Electron 测试**：单实例、动态端口、首启配置、窗口重启、退出清理和渲染进程隔离。
- **打包测试**：arm64 `.app` 与 `.dmg` 包含前端、服务端、migration、原子文件 helper 和 `better-sqlite3` 原生模块；对打包产物回归 CSP、导航阻断、session/CSRF、preload 白名单与未授权 loopback 请求。
- **模型测试**：自动化使用固定 DeepSeek 兼容夹具或假适配器；真实 DeepSeek 只做不写 vault 的人工连通性冒烟，不把实时模型输出当成可重复测试断言。

### 11.2 写入验收顺序

1. 自动化进程必须拒绝 `/Users/ao/我的大脑`、配置的正式 vault 和缺少测试哨兵的目录；写测试只接受 `mkdtemp` 创建且包含精确测试哨兵的临时 vault。
2. 所有写入先在独立测试 vault 验证。
3. 对每个故障窗口做进程终止测试，证明下次启动能确定识别状态；条件满足时可继续或回滚，否则安全停机并保留全部版本。
4. 正式 vault 先运行全量只读扫描并记录允许文件的 path、mtime 和 SHA-256。
5. 由用户选择一条现有 `未提炼` 资料，审阅完整写入差异。
6. 用户在交互式 App 中显式确认后执行一次受监督正式入库；测试和 CI 不能触发这一步。
7. 复读确认知识笔记、来源回链、状态、索引和正文原始字节保护。

未通过独立测试 vault 的写入能力，绝不能直接在正式 vault 上试验。

### 11.3 最终交付物

- 可安装的个人版 `.dmg`。
