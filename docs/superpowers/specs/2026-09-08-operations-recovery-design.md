# 操作与恢复：记录台与恢复工作单（已确认并实施）

## 定位

统一回答：刚刚做了什么、是否完成、未完成该如何继续。不是第二个回收站，不是原文存储区，也不提供任意历史回滚。

现状证据：OperationsPage 只显示固定空态；operationPageSchema 的 items 为 z.array(z.never())。真实归档、提炼、入库批次、回收记录各有现存服务与恢复流程，不能把空壳当成完整操作日志。

## 首页

- 顶部紧凑分段：需要处理 / 进行中 / 全部记录。首次有需处理项则选中该页，否则展示最近记录。待处理数量只来自已成功读取并判定的记录，源服务读取失败时显示“不完整”，不伪装为零。
- 主体是按真实时间排序的操作记录台，按天分组；无时间的旧归档记录独立归入“历史记录·时间未记录”，不编造时间。
- 一条记录呈现：资料标题、操作类型、时间、当前结果、一句说明。技术 ID 和路径收在展开详情里。
- 操作类型：资料归档、AI 提炼、知识入库、移入回收站、恢复、彻底删除。回收条目的多个阶段若缺少独立事件证据，只展示现有条目及可证实时间，不伪造完整事件链。
- 点记录才展开恢复工作单；默认不占用常驻右侧面板。工作单包含发生了什么、已完成部分、未完成原因、实际影响文件、下一步入口。

## 操作与状态

- 归档待核验：复用收件箱 intake.resume 能力，不重复归档。
- 最新提炼失败：查看原因，进入对应提炼工作台重新发起；不得自动调用 AI。旧失败若同一来源后续已成功，不继续计入需要处理。正常等待用户审阅的候选留在提炼队列，不冒充系统故障。
- 入库 writing / needs-review：复用批次读取、继续完成及恢复预览确认流程。committed 但 indexed=false 清楚说明文件已写入、只需更新检索。
- 回收相关异常：展示原因和定位入口；进入统一回收站核验。恢复已删除资料和彻底删除的唯一操作入口仍在回收站，此页只留历史与跳转。
- 成功记录只查看结果；已彻底删除记录不提供恢复。没有实际后端支持的撤销按钮不出现。
- 每个工作单只突出一个可执行下一步。进行中的记录先刷新状态，禁止重复提交；失败保留可读原因，完成后更新状态并归入历史。

## 数据实现要求

统一只读操作摘要应由后端从现有记录归一化；分页与来源覆盖必须明确，不能把最近 50 次提炼冒充全部历史。先确认各类记录时间、原路径、批次与来源映射、当前状态和可恢复能力；不要前端逐个请求每次提炼详情来拼完整日志。原操作系统为状态真源，不创建重复写入流程。

## 视觉方向

推荐“深色记录台 + 银色细节的恢复工作单”：时间轴负责来龙去脉，展开工作单负责处理。保留现有黑色底与银色光泽，但不再做另一个柜子；异常用少量琥珀色突出。替代方案是紧凑列表（更直接但弱化过程）或监控面板（状态多但对个人使用偏重）。

## 实施与验收

逻辑及视觉已获用户确认。已实现后端只读摘要、状态筛选及每页最多 100 条的分页、前端时间轴及按需工作单。归档复用 resume，已入库但未索引的批次复用索引续作，入库冲突跳转原批次，回收操作只跳转回收站。原有收据未保存日期的仍按未知日期显示。

分页在归一化并筛选后的轻量记录上执行；提炼与入库由数据库批量读取，不受原 list 的 50/200 条限制，归档历史独立读取全部收据。前端刷新从第一页重新读取；后续页面按 ID 去重。暂不新增历史存储或全局回滚。
