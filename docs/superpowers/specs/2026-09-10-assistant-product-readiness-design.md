# 问问作为资料入口：产品方案与验收条件

日期：2026-09-10。状态：**用户已明确批准方案后直接实施，正在执行**。实施进度见 [实施计划](../plans/2026-09-10-assistant-product-readiness.md)，已确认缺陷的修复、测试和实际运行版本另见就绪审查报告。未完成的验收项不作为已交付功能。

## 产品判断

用户提出的上下文用量、新对话、文件输入属于同一条使用流程：把资料带进来，知道 AI 此刻参考什么，再把有价值的结果留下。值得作为下一版问问的主线；继续堆更多视觉效果不能替代这条流程。

推荐工作流：

```mermaid
flowchart LR
  A[拖入文件 / 选择文件 / 粘贴文本] --> B[本地暂存与读取状态]
  B --> C[围绕文件问答与原文引用]
  C --> D{用户指令}
  D -->|归档| E[保存原件与可检索正文]
  D -->|提炼| F[归档来源并生成知识候选]
  E --> G[实际位置与操作回执]
  F --> H[审阅候选]
  H --> I[确认写入知识库]
```

资料只是临时阅读时不自动归档；已明确要求归档且目的地与文件无歧义时直接执行。资料分类、标题或指代不清时，在聊天内补齐缺少的信息。保留现有知识候选的正式入库审阅要求，不把“候选生成”说成“知识已入库”。

## 已有事实

- 已有按问题检索大脑、阅读原文、返回引用、准备提炼与保存候选的工具链，以及历史记录、停止、重试、继续上次。
- 新对话已存在；此前只有顶部加号，运行任务期间禁用。本轮将它改成可见文字入口。后端当前仍一次运行一个问问任务。
- 原始对话持久保存；每次请求仅发送最近 24 条历史消息，单对话达到 100 条消息后要求新建。这两项是当前应用限制，不是模型上下文容量。
- 当前没有附件请求字段、上传路由、解析器、附件账本、归档聊天工具，也没有 token usage/模型容量字段。
- 收件箱接收的是已有的 Markdown 主文件资料包。PDF 可以作为包内附件保留，但这不等于 AI 已读取 PDF 内容；单 PDF/纯 PDF 包当前不能走完整归档流程。

## 方案比较

| 方案 | 能做到什么 | 取舍 |
|---|---|---|
| 只在聊天里添加附件 | 临时读文件与提问 | 很快能看到按钮，但归档、提炼和恢复仍然断开，不满足此次目标。 |
| **统一资料入口，复用现有归档和候选流程** | 文件问答、来源归档、候选提炼、回执追踪 | 推荐。新增附件与解析层，继续使用已验证的文件事务。 |
| 扩展成任意文件系统 Agent | 自由移动、修改、处理整个电脑 | 范围过大，难以验证每个动作；不纳入此次产品主线。 |

## 1. 上下文圆环：显示本轮实际占用

- 放在输入区工具栏右侧，安静的单色细环，紧凑显示百分比。任务运行沿用现有边框流光，不让圆环承担加载动画。
- 点击展开“本轮上下文”：所用模型、容量、上一模型步骤的用量与更新时间、已带入的历史范围、附件及资料片段；明确区分“已选择”与“本轮实际读取”。
- 已有模型回执时显示实际数据；新输入或附件改变后显示“下一轮预计”，不继续把上次用量当实时精确值。尚无回执显示“待统计”；容量无法确认则显示 token 数和“容量未知”，不显示伪造百分比。
- 上下文占用按一次模型请求统计，多步骤工具调用的累计消耗另列“本次消耗”。本项目锁定 `ai@7.0.93`：精确单步取 `finish-step.usage` 或最后一项 `steps[].usage`，不能直接拿 `usage/totalUsage` 的累计值当当前上下文。
- 容量需按实际模型及版本核对并记录来源；模型 ID 在列表中出现并不能证明其容量。统一预算器计入系统提示、工具定义、选入历史、附件片段和输出预留。
- 超限时先说明哪部分超出，提供移除附件、缩小页码范围、带摘要开新对话。不会静默截断整个 PDF 后声称全文已读。
- 当前“只发最近 24 条”应在此显示实际保留范围。后续替换为按预算选择历史时，对摘要与略去内容保持可见。100 条消息上限是另一项限制，不能让低占用圆环掩盖它。

## 2. 新对话：用户知道什么会被带过去

- 顶部固定 `＋ 新对话`，历史入口独立。空白新对话不复制旧消息、附件或已固定来源；默认跟随当前页面的可选资料提示，但清楚标示尚未阅读。
- 保留旧对话、附件和操作回执，从历史中可找回；历史搜索覆盖全部已保存对话，不能只筛选最近 100 条。
- 未发送文本与附件选择按对话/草稿身份保存到本地，刷新或重启能够恢复。新建不会删除旧草稿；历史切换前完成当前草稿保存。
- “带摘要继续”作为独立次级动作：生成可编辑摘要，列出继续携带的文件，用户发送后才算启动新轮次。原始对话保留。
- 第一阶段沿用单任务执行：运行中明确显示“先停止或等待完成”。只有补齐跨会话运行状态、全局忙碌提示和恢复后，才开放“后台继续 + 新对话排队”；不先做一个看似可并发的按钮。

## 3. 文件输入：原件、解析内容和归档状态各有记录

### 用户操作

- 输入框 `＋` 提供“添加文件”“粘贴文本”，支持拖入；问问与收件箱的文件选择复用同一导入服务。
- 首批格式：文本 PDF、Markdown、TXT。扫描 PDF 检测到没有可用文字时显示“需要识别文字”，保留原件与重试入口；OCR 作为独立能力交付前不宣称已经支持。
- 附件条展示名称、大小、页数、读取状态，以及“仅本次对话 / 已归档”。读取中可取消，失败可重试，发送前可移除。问答与归档都能返回到原件。
- 大文件支持选择页码或章节，显示“本轮读取第 x–y 页”。多文件的引用明确对应文件和页码，不能只显示一个不知出处的 S1。
- 用户说“归档这个 PDF”：明确指代后给出归档位置；所需信息齐备时执行，并返回真实标题、路径、完成状态和打开入口。
- 用户说“提炼这个 PDF”：文件未归档则显示“将保留来源后生成候选”，使用相同归档流程，再提炼；已有归档直接复用。原始文件与导出文本作为可追溯来源，结果仍走现有候选审阅。
- 用户仅说“总结一下”则只回答。不能把临时阅读变成未经请求的全库收录。

### 实现边界

1. 新增按大脑与对话隔离的附件账本：`attachmentId`、内容哈希、原名、真实类型、尺寸、页数、状态、解析版本、派生文本、归档结果引用。暂存落在该大脑对应的应用数据目录；路径由服务分配，不让模型指定电脑绝对路径。
2. 上传入口传文件流，独立限制单文件/批次大小与解析资源，不把二进制塞入现有 JSON 消息。初始产品限制采用现有归档单文件 10 MiB、资料包 16 MiB 的上限；选择时展示同一份能力配置。需要更大文件必须先扩容归档协议再承诺。
3. 本地文本 PDF 解析保留页码；不执行 PDF 内脚本，不伪造 OCR。解析错误、密码保护、损坏、无文字、超限分别可见。下载第三方解析依赖后需锁版本并验证 Electron 打包。
4. AI 通过受限的 `list_attachments/read_attachment` 按页读取；附件文本视作证据，文件内的“归档/覆盖”等文字不能自己授予写入权限。
5. 用户明确归档指令绑定本轮允许动作与附件 ID，服务端核验；元数据完整后，经内部暂存包桥接现有归档事务。用户不需要安装插件或手工把文件移到 clipper 目录。
6. 不绕过现有原生事务直接写正式目录。未归档附件需先形成 Markdown 主文档 + 原 PDF 的资料包，主文档记录原件及文本提取来源；插件、问问、收件箱只作为来源渠道。
7. `prepare_extraction` 使用已归档主文档与版本快照，复用 `submit_candidates`、审阅和正式入库链路；超出当前提炼文本预算时显示分章提炼范围，不能截断后宣称整份已处理。
8. 归档/提炼阶段各自有持久 ID 与幂等回执。断网、重试或进程重启后先查已执行结果，不凭聊天文字猜测是否完成。文件已归档但提炼失败时从提炼阶段重试。
9. 从一段对话移除附件只解除引用；清理临时原件前检查其他对话和未完成任务的引用。已归档原件沿用现有回收/恢复流程。

当前 DeepSeek 官方 Files API 只支持图片文件，与当前文本模型组合不能直接获得 PDF 理解能力，因此本地解析是实际缺口。参见 [DeepSeek Files API](https://api-docs.deepseek.com/guides/files_api/) 与 [PDF.js 页面文本接口](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html)。模型用量优先使用 API 回执，估算不应冒充真实值，参见 [DeepSeek Token Usage](https://api-docs.deepseek.com/quick_start/token_usage/)。SDK 字段含义以本项目锁定版本的类型与实现为准。

## 由此延伸的优先改进

1. **上下文清单**：圆环能点开看到本轮带入了什么，一键移除不相关文件；切换“整个大脑/当前资料”不会让人误以为此前对话也被清空。
2. **能接着做的任务卡**：显示正在读文件、已归档、候选已保存、等待审阅、部分失败等实际阶段；在卡片内恢复失败步骤，不重新做已成功步骤。
3. **重复资料处理**：内容哈希相同时提示“已归档，继续问答/重新提炼”，同名但不同内容作为新版本处理；不悄悄覆盖原件。
4. **回答可直接变成下一步**：复制、引用原文、生成提纲、转成候选；展示是对话产物还是已确认知识。已有选段追问继续沿用。
5. **启动就绪检查**：把大脑可读、模型可用、文件可解析分开显示；配置变更后可以测试连通，失败定位到具体步骤。当前模型列表可读只证明接入状态，不证明一次真实生成已成功。

对话改名、导出以及跨会话检索正文可后续补充。首版不扩展任意网页抓取、批量 OCR、任意电脑文件修改或多 Agent 并发，以免资料主流程长期不能交付。

## 验收清单与交付顺序

1. 先修复本轮确认的旧状态/历史检索问题并复核实际桌面版本。
2. 接入单步用量与预算，完成圆环、范围清单、新对话与草稿恢复；用无 usage、模型切换、超预算、长历史、停止/重试的隔离用例验证。
3. 附件本地账本、文本 PDF/MD/TXT 解析、问答引用：包含损坏/扫描/加密 PDF、取消、重复、重启、多文件页码对照。大文件必须可说明实际阅读范围。
4. 将聊天指令接入归档与提炼：文本 PDF 从拖入到归档、生成候选、人工审阅、打开知识完成一次端到端验收；确认原 PDF 哈希不变。
5. 故障验收：归档提交后的响应丢失、提炼失败、关闭应用、重复指令，恢复后无重复原件/候选，回执能定位真实成果。
6. 从新构建的独立 `.app` 冷启动验收。覆盖已有库升级、选择有效大脑、模型配置与一次真实生成；测试资料使用独立库。当前开发运行窗口可用，不代表旧打包文件已更新。

“可直接用”的完成标准是这条链路通过，不能由测试总数、按钮数量或光效替代。
